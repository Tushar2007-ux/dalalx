Part 1

The idea in one page

Object-Oriented Modelling means building software out of objects: small units that each hold some data and the behaviour that belongs with it, and that talk to each other through clear interfaces.

The test of a good object-oriented design is not "did we use classes". It is: when something new is needed, how much existing code do we have to change? In a good design the answer is "very little", because each new thing is a new object that plugs into a place made for it.

Uncross was built to pass that test, and it has a real track record to prove it. After the first version was finished, fourteen features were added (two order types, accounts, a journal, news, a tournament, a new surveillance rule and more), and each one arrived mostly as new classes plugged into existing interfaces.

The sentence to remember"Every feature in Uncross is an object that plugs into an interface. New order type: a new Strategy. New bot: a new subclass. New feature that reacts to trades: a new Observer. The engine itself rarely changes."

Part 3 · Pillar 1

Encapsulation

An object keeps its data private and only lets the outside world change it through methods that check the change is valid. The object protects its own rules.

Example 1: an Order cannot be put into an impossible state

Every field of Order is private. Nobody can write order.remainingQty = -5. The only way to reduce what is left is fill(), which refuses anything invalid and updates the status in the same step:

// core/.../model/Order.java
private long remainingQty;
private OrderStatus status;

public void fill(long qty) {
    requireActive("fill");                    // can't fill a cancelled order
    if (qty <= 0 || qty > remainingQty) {
        throw new IllegalArgumentException(...); // can't overfill
    }
    remainingQty -= qty;
    status = remainingQty == 0 ? OrderStatus.FILLED : OrderStatus.PARTIALLY_FILLED;
}

Notice there is reduceTo() but deliberately no "grow" method. A bigger order would be cutting in line, so the class simply does not offer it. The rule of the market is built into the shape of the object.

Example 2: OrderBook hides how it stores orders

Inside, the book uses two TreeMaps (bids sorted high-to-low, asks low-to-high) and a HashMap from id to order. None of that is visible. Outsiders only see meaningful operations: add, remove, peekBest(side), fillBest(side, qty), bestBid(), snapshot(depth). We could replace the TreeMaps with arrays tomorrow and no other class would notice.

Example 3: behaviour lives with its data

public enum Side {
    BUY, SELL;
    public Side opposite() { return this == BUY ? SELL : BUY; }
}

The fact that buy and sell are opposites lives inside Side, instead of being repeated as if statements across the matching code.

Example 4: an account guards its own money

Account's check-and-reserve methods (reserveBuy, reserveSell) are synchronized and package-private. Only the risk desk in the same package can call them, and the check ("is there enough free cash?") and the reservation happen as one indivisible step.

How to say it"Encapsulation in Uncross means an object enforces its own rules. You cannot overfill an Order, grow it in place, or spend an Account's money twice, because the class does not give you a way to."

Part 4 · Pillar 2

Abstraction

Abstraction means depending on what something does, not how it does it. In Java this is mostly done with interfaces.

InterfaceWhat it promisesWho uses it without knowing the details
MatchingStrategymatch(order, book) returns a resultSymbolEngine never knows which order type it is matching.
MatchingEnginesubmit, cancel, snapshot for one stockThe worker thread that drives it.
MarketStatewhat is allowed now, and what comes nextTradingSession.
EngineListeneronEvent(event)The EventBus, which has 10+ different listeners.
TradingBotact(context) each tickBotRunner, which runs every bot the same way.
MarketView / OrderGatewayread prices / send ordersBots. They never touch the Exchange directly.
SurveillanceRuleinspect(event, activity) returns findingsSurveillanceDesk.

The best example is how bots see the market. A bot receives a BotContext holding only a MarketView (to read prices) and an OrderGateway (to send orders). It has no idea the exchange has worker threads, queues, a journal or a risk desk. In tests we hand the bot a fake view and gateway, and it cannot tell the difference.

Part 5 · Pillar 3

Inheritance

A subclass reuses and specialises a parent class. Uncross uses inheritance carefully: only where the children truly are "a kind of" the parent and share real code.

Five matchers share one matching loop

AbstractOrderMatcher holds the loop every order type shares: "while the order still wants shares and the best opposite price is acceptable, trade with it". Each subclass fills in only what makes it different.

Eight bots share one base

AbstractBot gives every bot its id, name, tuning and helper methods for placing limit and ioc orders, and for withdrawing its orders. Each bot (Market Maker, Momentum, Panic Seller, Whale, Contrarian, Noise, Spoofer, and the user-built RuleBot) only writes act(): its own decision.

Inheriting from the Java library

  • ReplayClock extends Clock: during recovery, the engine is handed a clock pinned to each journal entry's time. The engine just asks "what time is it?" and does not know it is being replayed.
  • UnknownSymbolException extends IllegalArgumentException: a specific, meaningful exception instead of a generic one.

Using final to stop inheritance where it does not belong

Almost every concrete class is final, and the shared methods in the abstract parents are final too (for example AbstractOrderMatcher.match, AbstractBot.name). A subclass may fill in the blanks it is given, but may not rewrite the algorithm. This follows the advice "design for inheritance, or else prohibit it".

Composition is preferred elsewhere

Where "is-a" does not truly hold, the design uses composition instead. SymbolEngine is not a kind of order book; it has an order book, a factory, strategies and a trading session. RiskDesk is not a subclass of anything; it implements two interfaces. "Favour composition over inheritance" is visible throughout.

Part 6 · Pillar 4

Polymorphism

One call, many behaviours: the same method call does different things depending on the actual object behind it, chosen at run time.

The single most important line in the engine

// core/.../matching/SymbolEngine.java
MatchResult result = strategies.forType(order.type()).match(order, book);

There is no if (type == LIMIT) ... else if (type == MARKET) .... The registry hands back the right object, and calling match on it runs Limit, Market, IOC, Stop-loss or Iceberg behaviour. This is runtime (dynamic) polymorphism, by overriding.

Without polymorphism

switch (order.type()) {
  case LIMIT  -> matchLimit(order);
  case MARKET -> matchMarket(order);
  case IOC    -> matchIoc(order);
  // every new type: edit here,
  // and in every other switch
}

With polymorphism (Uncross)

strategies.forType(order.type())
          .match(order, book);
// a new type is a new class;
// this line never changes

More of the same idea

  • Market status: state.onClock(now). OpenState returns itself; HaltedState returns itself until the halt ends, then the next state. The caller just keeps whatever comes back.
  • Events: listener.onEvent(event) sends the same event to the surveillance desk, the risk desk, the candle chart and the headline writer, and each does something completely different.
  • Bots: bot.act(context) once per tick, for every bot, no matter which kind.
  • Surveillance: rule.inspect(event, activity) for each of the five rules.

Compile-time polymorphism too

Overloading (same name, different parameters) appears as well: MarketState has both refusal() and refusal(OrderType). The second, a default method, normally just calls the first, but AuctionState overrides it to accept only limit orders during an auction.

Part 8

The SOLID principles

Five rules for designs that stay easy to change. Each one has a concrete home in Uncross.

S — Single Responsibility

A class should have one reason to change.

The matching work is split so each class has one job. OrderBook stores orders. A matcher decides how one order type trades. OrderFactory builds valid orders. CircuitBreaker watches price speed. SymbolEngine coordinates them. The stop-loss feature is split the same way: StopBook decides when a stop fires, and StopLossOrderMatcher decides how it trades. Two small classes instead of one confused one.

O — Open/Closed

Open for extension, closed for modification.

The flagship example. Adding stop-loss and iceberg needed zero edits to the existing matchers: two new classes and two lines in the registry.

// core/.../matching/MatchingStrategies.java
map.put(OrderType.LIMIT,     new LimitOrderMatcher(tradeIds, clock));
map.put(OrderType.MARKET,    new MarketOrderMatcher(tradeIds, clock));
map.put(OrderType.IOC,       new IocOrderMatcher(tradeIds, clock));
map.put(OrderType.STOP_LOSS, new StopLossOrderMatcher(tradeIds, clock)); // added later
map.put(OrderType.ICEBERG,   new IcebergOrderMatcher(tradeIds, clock));  // added later

The same holds for bots (a new bot is a new subclass), surveillance (front-running was added as one new SurveillanceRule) and features that react to trades (a new EngineListener).

L — Liskov Substitution

Anywhere a parent type is expected, any child must work correctly.

Any of the five matchers can be handed to SymbolEngine; any of the eight bots can be run by BotRunner; any MarketState can be held by TradingSession. The engine's tests run the same scenarios through different implementations. The abstract parents make substitution safe by keeping the shared algorithm final, so a child cannot break it.

I — Interface Segregation

Prefer several small interfaces to one big one.

Bots get two narrow interfaces, MarketView (read) and OrderGateway (trade), instead of the whole Exchange. EngineListener has exactly one method. OrderGate has exactly one method. LiveMarketView shows the other side: one class implementing MarketView, FairValues and EngineListener, so each user sees only the slice it needs.

D — Dependency Inversion

High-level code depends on abstractions, not on details.

  • Within the core: SymbolEngine depends on MatchingStrategy, not on any concrete matcher. The exchange depends on Journal and OrderGate, not on files or accounts.
  • Between modules: core has no Spring import anywhere. The Spring server depends on the core, never the reverse. The web is a detail plugged in from outside.
  • Time is injected: classes receive a Clock instead of calling the system clock. That is what lets recovery replay the past with a ReplayClock, and lets tests control time exactly.
A quick way to show all five"Single responsibility: StopBook versus StopLossOrderMatcher. Open/Closed: the registry. Liskov: any matcher in SymbolEngine. Interface segregation: bots see MarketView and OrderGateway, not the Exchange. Dependency inversion: no Spring in core, and an injected Clock."

Part 9

Design patterns

A design pattern is a named, proven solution to a common design problem. Every pattern here is named in the Javadoc of the class that uses it.

1. Strategy

Problem: several ways of doing one job, chosen at run time. Solution: put each way in its own class behind one interface.

In Uncross: order matching (5 matchers behind MatchingStrategy), bot behaviour (8 bots behind TradingBot), order checks (OrderGate), and even the trigger of a user-built bot: the When enum (FALLS / RISES / EVERY) gives each constant its own behaviour.

2. Template Method

Problem: several classes share an algorithm but differ in a few steps. Solution: the parent writes the algorithm once in a final method and calls abstract "hook" methods for the steps that vary.

// AbstractOrderMatcher — the template
public final MatchResult match(Order incoming, OrderBook book) {
    validate(incoming, book);
    List<Trade> trades = new ArrayList<>();
    while (incoming.isActive() && bestIsAcceptable(incoming, book, ...)) {
        trades.add(tradeWithBest(incoming, book, ...));  // always at the RESTING price
    }
    return finish(incoming, book, trades);              // hook: rest? cancel? 
}
protected abstract OrderType handledType();                   // hook
protected abstract boolean acceptsPrice(Order in, long price);  // hook
protected abstract MatchResult finish(...);                     // hook

Limit, Market and IOC differ only in the hooks: Market accepts any price; Limit and IOC accept prices within the limit; Limit's finish rests the remainder, IOC's cancels it.

3. Factory

Problem: creating an object correctly needs several steps that should not be repeated everywhere. Solution: one class whose job is creating.

In Uncross: OrderFactory.create(request) gives each new Order its id, sequence number and timestamp from injected sources. MatchingStrategies.standard(...) is a static factory method building the registry; StandardBots builds the regular bot cast.

4. Observer

Problem: many parts of the system must react when something happens, without the source knowing about them. Solution: the source publishes events; observers register to receive them.

The bus uses a CopyOnWriteArrayList for listeners: events are published constantly while registrations are rare, so iterating needs no lock. One failing listener cannot stop the others.

5. State

Problem: an object behaves differently depending on its situation, and if checks spread everywhere. Solution: each situation is its own object, and the object swaps its current state.

// HaltedState decides its own next state
public MarketState onClock(Instant now) {
    return now.isBefore(endsAt) ? this : reopen.apply(now);
}

6. Command

Problem: requests need to be queued, logged and replayed. Solution: turn each request into an object.

In Uncross: every submit, cancel and amend becomes a Command object placed on the stock's queue. The same commands are written to the journal as JournalEntry records and replayed through the same engine on restart (Recovery) or into a private exchange (Rewind). A request that is an object can be stored, sent to another thread, and run again later.

7. Singleton

OpenState has no data, so one shared instance is enough: OpenState.INSTANCE, with a private constructor so no one can make another.

8. Null Object

OrderGate.OPEN is a gate that refuses nothing. Code can always call a gate without checking for null; when there is no risk desk, the "do nothing" gate is used.

9. Composite

OrderGate.allOf(gateA, gateB, ...) combines several gates into one object that is itself an OrderGate. The exchange still sees one gate, whether it is one rule or many.

10. Adapter

Problem: two parts expect different interfaces. Solution: a small class that translates.

ExchangeGateway adapts the Exchange (asynchronous, returns futures) to the simple OrderGateway interface bots expect. At a larger scale, the whole server module is a set of adapters: Spring controllers translate HTTP and WebSocket messages into core calls.

11. Facade

Exchange is a single front door to a complex subsystem: workers, queues, engines, journal, gates. Callers use a handful of methods (submit, cancel, amend, snapshot, list) and never see the machinery behind them.

Part 10

Modern Java features that support the design

Records = immutable value objects

Trade, OrderRequest, every event, BookSnapshot, BotRecipe. Fields are final; equality is by value; equals, hashCode, toString come free. Immutable objects are safe to share between threads.

Sealed interfaces = a closed family

EngineEvent and JournalEntry list exactly which records may implement them (permits ...). The compiler then knows every case, so a switch over events can be checked for completeness.

Pattern-matching switch

BotLedger.onEvent does switch (event) { case TradeExecuted e -> ...; case OrderAccepted e -> ...; }: type test and cast in one safe step.

Enums with behaviour

Side.opposite(); the bot-recipe When enum where each constant implements its own trigger logic. Type-safe: a typo like "BUUY" cannot compile.

Functional interfaces and lambdas

EngineListener and OrderGate have one method each, so a small listener or gate can be a lambda. OrderGate.allOf returns a lambda.

Optional instead of null

peekBest() returns Optional<Order>; refusal() returns Optional<String>. "Nothing here" is explicit in the type.

long paise, never double

Money is a long number of paise: ₹102.50 is 10250. Exact arithmetic, no rounding errors. The Money class formats it for display.

No Lombok, no framework in core

Every getter and constructor is visible plain Java, so the design can be read and examined directly.

Part 11

Objects and threads: ownership as a design decision

In object-oriented terms, the concurrency model is a rule about which object owns which other object, and who may talk to it.

  • Each stock has one SymbolWorker, which owns one SymbolEngine, which owns one OrderBook. Ownership is strict composition.
  • The worker is the only thread that ever touches that book. This is thread confinement, and it is why OrderBook is deliberately not thread-safe and needs no locks.
  • Everyone else talks to the worker by message: they put a Command object into its BlockingQueue and get back a CompletableFuture (a promise of the result). This is producer–consumer.
  • Objects that cross threads are immutable records (events, snapshots, trades), so sharing them is safe by construction.
  • The few objects that really are shared (an Account used by several stocks' workers, the list of workers) protect themselves: synchronized methods, or copy-on-write with a volatile reference.
How to say it"Our concurrency design is really an encapsulation decision: each order book belongs to exactly one thread, other code sends it messages, and what crosses between threads is immutable."

Part 12

Case study: how Iceberg was added

The best evidence of good OOM is a real change. Walk through this one in the viva.

  1. Model it. An iceberg is a limit order that shows only a slice (displayQty) at a time. So it needs a displayQty in the request and slice-tracking in Order (visibleQty(), sliceUsedUp(), showNextSlice()), all encapsulated in the order itself.
  2. Add the type. One new constant ICEBERG in the OrderType enum.
  3. Write the strategy. IcebergOrderMatcher extends AbstractOrderMatcher, supplying the three hooks. The shared matching loop is inherited, untouched.
  4. Register it. One line in MatchingStrategies.standard.
  5. Keep it fair. When a slice is used up, PriceLevel sends the next slice to the back of the queue, so hidden size never jumps the line. That rule lives in the class that owns the queue.
  6. Test it. JUnit tests for slicing, queue position and partial fills, while every older test kept passing.

Not touched: LimitOrderMatcher, MarketOrderMatcher, IocOrderMatcher, SymbolEngine's dispatch line, the event system, the bots, surveillance. That list of untouched classes is the Open/Closed principle.

Part 14

Viva questions on OOM

What is the difference between Strategy and State? Both look the same in a diagram.

The structure is the same (an interface with several implementations), but the intent differs. With Strategy, the caller chooses the behaviour (the order's type picks the matcher), and strategies do not know about each other. With State, the object changes its own state over time, and states know their successors: HaltedState.onClock returns the next state itself.

Why an abstract class for matchers and not just the interface?

The interface defines the contract; the abstract class holds the shared loop so it is written once. Other code depends only on the interface (MatchingStrategy), so a completely different matcher could still implement it directly without extending the abstract class.

Abstract class versus interface: when do you use which?

An interface for a role many unrelated classes can play (EngineListener is implemented by surveillance, risk and charts, which have nothing else in common). An abstract class when the children share real code and state (AbstractBot shares id, tuning and order helpers).

Composition or aggregation between SymbolEngine and OrderBook?

Composition. The engine creates the book, owns it alone, and the book has no life without it. Contrast with EventBus and its listeners: listeners are created elsewhere and outlive registration, so that is aggregation.

Why is Order a class but Trade a record?

An order changes over its life: it fills, partially fills, or is cancelled, so it is a mutable class that guards its changes. A trade is a fact that happened and never changes, so it is an immutable record.

Where is polymorphism in your project?

Most clearly in strategies.forType(order.type()).match(order, book): one call runs one of five behaviours depending on the object. Also listener.onEvent, bot.act, state.onClock and rule.inspect.

Show me the Open/Closed principle.

Open MatchingStrategies.standard. Stop-loss and iceberg were added later as two new classes and two lines here; no existing matcher was modified, and all earlier tests kept passing.

How does your design make testing easier?

Because classes depend on interfaces and injected values, tests swap in simple fakes: a fixed Clock, a counter for ids, a fake MarketView for a bot. The core has no framework, so its tests run in seconds without starting a server.

Why are most classes final?

A class not designed for extension can be broken by a subclass that overrides something it relied on. Making it final states the intent clearly. The abstract parents are the deliberate exceptions, and even there the shared algorithm is final.

Your OrderBook is not thread-safe. Isn't that bad design?

It is deliberate. The book is confined to one worker thread, which owns it. Adding locks would cost speed and protect against something that cannot happen. The rule is documented in the class's comments wherever it matters.

Which pattern lets you recover after a crash?

Command. Each request is an object, so it can be written to the journal and replayed through the same engine later. Dependency inversion helps too: a ReplayClock is injected so replayed trades keep their original times.

Where is the Factory pattern and why do you need it?

OrderFactory.create(request). Every order must get a unique id, a sequence number for time priority, and a timestamp. Putting that in one class means no code path can build an order missing them.
