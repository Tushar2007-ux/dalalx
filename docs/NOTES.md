# DalalX — Build Notes

## Step 0 — Project skeleton
- **What was set up:** a Maven multi-module build (root `pom.xml` aggregating `core` and `server`, Java 21, JUnit 5 + AssertJ), a Vite + React + TypeScript frontend, and `run.sh` to start both. A first end-to-end path works: browser → Vite dev proxy (`/api` → `localhost:8080`) → Spring Boot `GET /api/health` → `{"status":"ok"}`, with tests at each layer.
- **What each module does:** `core` is the plain-Java exchange (engine, order books, bots, breaker, auction, surveillance, headlines); `server` is a thin Spring Boot adapter that turns HTTP/WebSocket traffic into calls on `core`; `frontend` is the React UI ("The Morning Edition") that talks only to `server`.
- **Why `core` has no Spring dependency:** separation of concerns and the Dependency Inversion Principle. The domain logic shouldn't depend on a delivery framework, so `core` can be unit-tested as plain Java (fast, no container), reasoned about without "framework magic", and reused behind any other adapter (CLI, desktop, a different web framework). The dependency points one way only: `server → core`, never `core → server`. This is enforced by the build: only `server/pom.xml` imports the Spring Boot BOM.
- **Design choices already visible:** the health response is an immutable `record` (a value object with no setters); the server is an *adapter* in the Ports & Adapters (Hexagonal) sense; the Vite proxy gives the browser a single origin, so no CORS configuration is needed.
- **Likely examiner question:** *"Why a multi-module build instead of one project with packages?"* — *Answer:* packages are only a naming convention, so nothing stops a class in `engine` importing Spring. Separate Maven modules make the boundary a compile-time rule: `core` literally cannot see Spring classes because they aren't on its classpath. Each module can also be built and tested on its own.

## Step 1 — Domain model
- **Encapsulation in `Order`:** all fields are `private` and there are no setters. State changes only through `fill(qty)`, `cancel()` and `reject()`. Each method checks the rules first and throws (`IllegalStateException` for a wrong status, `IllegalArgumentException` for a bad quantity) *before* changing anything, so an order can never get into an impossible state such as "FILLED with 10 shares remaining". It is also built from an already-validated `OrderRequest`, so bad input can't get in. It's deliberately not thread-safe: each symbol's worker thread owns its orders (thread confinement).
- **Why prices are `long` paise:** `double` is binary floating point and can't store 0.10 exactly, so money sums drift (0.1 + 0.2 ≠ 0.3) and price comparisons in the book could be wrong. Integer paise (₹102.50 = `10250`) are exact, compare with `==`, and `Math.multiplyExact`/`addExact` throw on overflow instead of silently wrapping. `Money.format` is the single place where paise become `₹2,97,780.00`.
- **Why `Trade` is a record:** a trade is a fact that has already happened and must never change, so it's an immutable value object. A `record` gives final fields, accessors, and value-based `equals`/`hashCode`/`toString` with no boilerplate. Its compact constructor rejects impossible trades (price or qty ≤ 0, self-trade). Because it's immutable, it can be safely shared with many observers (ticker, headlines, surveillance) on other threads.
- **Order status lifecycle:** NEW → PARTIALLY_FILLED / FILLED / CANCELLED / REJECTED, and PARTIALLY_FILLED → PARTIALLY_FILLED / FILLED / CANCELLED. FILLED, CANCELLED and REJECTED are terminal (`isTerminal()`). Only NEW can be rejected, because traded shares can't be un-traded. Every legal transition has a test, and every illegal one is tested from each status it's illegal from (89 tests in total).
- **Likely examiner question:** *"Why is `Order` a class but `Trade` a record?"* — *Answer:* `Order` is an *entity*: it has an identity (its id) and its state changes over time, so it needs encapsulated mutable fields and equality by id (a part-filled order is still the same order). `Trade` is a *value object*: it never changes, so it's equal to another trade with the same values, and a record models that exactly.
