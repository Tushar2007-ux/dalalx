# DalalX — Build Notes

## Step 0 — Project skeleton
- **What was set up:** a Maven multi-module build (root `pom.xml` aggregating `core` and `server`, Java 21, JUnit 5 + AssertJ), a Vite + React + TypeScript frontend, and `run.sh` to start both. A first end-to-end path works: browser → Vite dev proxy (`/api` → `localhost:8080`) → Spring Boot `GET /api/health` → `{"status":"ok"}`, with tests at each layer.
- **What each module does:** `core` is the plain-Java exchange (engine, order books, bots, breaker, auction, surveillance, headlines); `server` is a thin Spring Boot adapter that turns HTTP/WebSocket traffic into calls on `core`; `frontend` is the React UI ("The Morning Edition") that talks only to `server`.
- **Why `core` has no Spring dependency:** separation of concerns and the Dependency Inversion Principle. The domain logic shouldn't depend on a delivery framework, so `core` can be unit-tested as plain Java (fast, no container), reasoned about without "framework magic", and reused behind any other adapter (CLI, desktop, a different web framework). The dependency points one way only: `server → core`, never `core → server`. This is enforced by the build: only `server/pom.xml` imports the Spring Boot BOM.
- **Design choices already visible:** the health response is an immutable `record` (a value object with no setters); the server is an *adapter* in the Ports & Adapters (Hexagonal) sense; the Vite proxy gives the browser a single origin, so no CORS configuration is needed.
- **Likely examiner question:** *"Why a multi-module build instead of one project with packages?"* — *Answer:* packages are only a naming convention, so nothing stops a class in `engine` importing Spring. Separate Maven modules make the boundary a compile-time rule: `core` literally cannot see Spring classes because they aren't on its classpath. Each module can also be built and tested on its own.

## Step 1 — Domain model
- **Encapsulation in `Order`:** all fields are `private` and there are no setters. State changes only through `fill(qty)`, `cancel()` and `reject()`. Each method checks the rules first and throws (`IllegalStateException` for a wrong status, `IllegalArgumentException` for a bad quantity) *before* changing anything, so an order can never get into an impossible state such as "FILLED with 10 shares remaining". It is also built from an already-validated `OrderRequest`, so bad input can't get in. It's deliberately not thread-safe: each symbol's worker thread owns its orders (thread confinement).
- **Why prices are `long` paise:** `double` is binary floating point and can't store 0.10 exactly, so money sums drift (0.1 + 0.2 ≠ 0.3) and price comparisons in the book could be wrong. Integer paise (₹102.50 = `10250`) are exact, compare with `==`, and `Math.multiplyExact`/`addExact` throw on overflow instead of silently wrapping. `Money.format` is the single place where paise become `₹2,97,780.00`.
- **Why `Trade` is a record:** a trade is a fact that has already happened and must never change, so it's an immutable value object. A `record` gives final fields, accessors, and value-based `equals`/`hashCode`/`toString` with no boilerplate. Its compact constructor rejects impossible trades (price or qty ≤ 0, self-trade). Because it's immutable, it can be safely shared with many observers (ticker, headlines, surveillance) on other threads.
- **Order status lifecycle:** NEW → PARTIALLY_FILLED / FILLED / CANCELLED / REJECTED, and PARTIALLY_FILLED → PARTIALLY_FILLED / FILLED / CANCELLED. FILLED, CANCELLED and REJECTED are terminal (`isTerminal()`). Only NEW can be rejected, because traded shares can't be un-traded. Every legal transition has a test, and every illegal one is tested from each status it's illegal from (89 tests in total).
- **Likely examiner question:** *"Why is `Order` a class but `Trade` a record?"* — *Answer:* `Order` is an *entity*: it has an identity (its id) and its state changes over time, so it needs encapsulated mutable fields and equality by id (a part-filled order is still the same order). `Trade` is a *value object*: it never changes, so it's equal to another trade with the same values, and a record models that exactly.

## Step 2 — Order book and limit matching
- **Why `TreeMap` and `ArrayDeque`:** the book needs two kinds of order. Across prices, a `TreeMap` keeps price levels *sorted* (bids with `Comparator.reverseOrder()`, so the highest is first; asks ascending, so the lowest is first), and the best price is just `firstEntry()`. A `HashMap` would be unordered, and a sorted `ArrayList` would need O(P) shifting on every insert. Within one price, an `ArrayDeque` is a FIFO queue: add at the back and fill from the front, both O(1), with no per-node overhead like `LinkedList`. A separate `HashMap<Long, Order>` gives O(1) lookup by id, so a cancel doesn't have to search every level.
- **Time complexity** (P = number of price levels, n = orders at one price, k = trades produced): **add/rest** is O(log P) for the TreeMap lookup or insert, plus O(1) for the deque and the index. **match** is O(k log P): each trade peeks at and fills the best level, and may remove an emptied level. **cancel** is O(1) to find the order by id, O(log P) to find its level, and O(n) to remove it from the deque, which has to scan. Best bid/ask is O(log P), and `snapshot(d)` is O(log P + d).
- **Price-time priority:** a resting order with a better price always trades first (the TreeMap ordering). At the same price, the earliest arrival trades first (the FIFO deque). A partial fill leaves an order at the front, so it keeps its place in the queue. This rewards traders who quote aggressive prices, and those who quote early.
- **Why trades execute at the resting price:** the resting order arrived first and publicly displayed its price. The incoming order *accepted* that price by crossing the spread. So a buy limit of ₹105 against an ask of ₹100 trades at ₹100: the aggressor gets *price improvement*, and the resting trader gets exactly the price they asked for. Neither side ever trades worse than its own limit. The randomized test checks this for every trade.
- **Likely examiner question:** *"How do you know the matching engine is correct, not just that it passes a few examples?"* — *Answer:* besides one test per scenario, a randomized test submits 10,000 random orders with random cancels (3 fixed seeds, so it's reproducible). After every step it checks that the book is never crossed. At the end it checks invariants that must always hold: filled + remaining = original for every order, each order's fills equal its trades, every trade is at the resting price and within both limits, and level totals equal the remaining quantity of the active orders. I also broke the code on purpose (trading at the incoming price, and filling LIFO instead of FIFO), and the tests failed both times, so they really detect bugs.

## Step 3 — Order-type strategies, factory and cancels
- **Strategy pattern:** each order type has its own matcher (`LimitOrderMatcher`, `MarketOrderMatcher`, `IocOrderMatcher`) behind the `MatchingStrategy` interface. `SymbolEngine` asks `MatchingStrategies` for the right one and calls `match()`. There is no `if/switch` on order type anywhere in the engine.
- **Template Method (bonus pattern):** the three types share one matching loop: walk the opposite side best-first, trading at the resting price, while the price is acceptable. That loop lives once, as a `final` method in `AbstractOrderMatcher`. Subclasses only answer two questions: *is this price acceptable?* (`acceptsPrice`) and *what happens to the leftover?* (`finish`). LIMIT checks its limit and rests the rest; IOC checks its limit and cancels the rest; MARKET accepts any price, cancels the rest, and is *rejected* if the book is empty.
- **Factory + Open/Closed:** `OrderFactory` is the only place an `Order` is created, so ids, arrival sequences and timestamps can't be faked or collide. `MatchingStrategies` maps each `OrderType` to its matcher in an `EnumMap`. Adding Fill-or-Kill means one enum constant, one new class `FokOrderMatcher`, and one `put` line. No existing matcher or engine code changes. That's the Open/Closed principle: open for extension, closed for modification.
- **Cancels and the `MatchingEngine` interface:** callers use the `MatchingEngine` interface (`submit`, `cancel`, `snapshot`) and never see the book or matchers (abstraction). A cancel removes a resting order in O(1) by id. If the order has already filled, been cancelled or been rejected, the cancel returns a `CancelResult` with a clear reason instead of throwing, because "cancel arrived just after the fill" is a normal race on real exchanges, not a bug. The engine remembers recent orders in a size-bounded `LinkedHashMap`, so memory can't grow forever.
- **Likely examiner question:** *"How do LIMIT, MARKET and IOC differ? Give an example."* — *Answer:* for BUY 100 @ ₹103 against asks of 50 @ ₹102 and 80 @ ₹105: LIMIT buys 50 @ ₹102 and the other 50 rest as a bid at ₹103; IOC buys 50 @ ₹102 and cancels the other 50; MARKET (no limit) buys 50 @ ₹102 and 50 @ ₹105. All three trade at the resting prices, and all three are tested with exactly this example.

## Step 4 — Event stream (Observer)
- **Observer pattern:** `SymbolEngine` is the *subject*. It publishes what happened to an `EventBus`, which forwards each event to every registered `EngineListener` (the *observers*). The engine only knows the one-method `EngineListener` interface, never the WebSocket bridge, surveillance, headlines or bots. Dependencies point one way: those features depend on the engine, never the reverse. New features plug in by registering a listener, with no change to engine code (Open/Closed again).
- **Fixed event order for every command:** `OrderAccepted → TradeExecuted × n → OrderCancelled/OrderRejected (if any) → BookChanged (if the book changed)`. A market order with nobody to trade against publishes only `OrderRejected`. A trader's cancel publishes `OrderCancelled → BookChanged`, and a failed cancel publishes nothing. Every event carries a global, strictly increasing `sequence`, so listeners can always tell which happened first.
- **Sealed, immutable events:** `EngineEvent` is a `sealed interface` that permits exactly five record types, so a `switch` over events is checked by the compiler for missing cases. Events carry `OrderView`, a frozen copy of the order, rather than the live `Order` entity. The live order belongs to one worker thread and keeps changing, while events are read by other threads later, so they must contain only values that can't change.
- **Why `CopyOnWriteArrayList`, and listener isolation:** events are published constantly but listeners register rarely. This list makes reads (iteration) lock-free and immune to `ConcurrentModificationException`, at the cost of copying on each write, which is the right trade-off here. Each listener call is wrapped in `try/catch`, so one buggy listener is logged and skipped, and the rest still receive the event.
- **Likely examiner question:** *"What's the difference between Observer and just calling the UI from the engine?"* — *Answer:* direct calls would make the engine depend on every consumer: adding surveillance would mean editing the matching code, and the engine couldn't be tested without a UI. With Observer, the engine publishes to an interface and doesn't know or care who is listening. Consumers can be added, removed or tested in isolation (the tests use a `RecordingListener`), and a failure in one consumer can't break matching.

## Step 5 — Multi-stock concurrency
- **Thread confinement:** each stock has exactly one `SymbolWorker` thread (`worker-RELIANCE`, `worker-TCS`, …) that owns its `SymbolEngine` and order book. No other thread ever touches a book. Requests from anywhere (REST, bots, tests) are wrapped as `Command`s and put on that worker's queue, and the worker runs them one at a time, in arrival order. So the book needs no locks, can never be corrupted by two threads at once, and arrival order (fairness) is guaranteed. Different stocks have different threads, so they really do match in parallel on different cores.
- **Producer–consumer with a `BlockingQueue` (the OS bounded-buffer problem):** many producers `put()` commands and one consumer `take()`s them. `take()` sleeps while the queue is empty (no busy-waiting), and `put()` sleeps once 100,000 commands are waiting (back-pressure). `LinkedBlockingQueue` does the mutex and condition-variable work internally, which is exactly what we wrote by hand with `pthread_mutex` and `pthread_cond` in the OS lab. Shutdown uses a *poison pill*: stop accepting, enqueue a special command, let everything ahead of it finish, then exit.
- **Command pattern + futures:** every request becomes a `Command` object (an action plus a `CompletableFuture` for the answer). The caller gets the future immediately and can `join()` or attach a callback, while the worker runs the action later. An exception inside a command completes the future exceptionally, so the caller sees the error and the worker keeps running. The only shared state is an `AtomicLong` (lock-free unique ids) and a small synchronised order-id → symbol map used to route `cancel(id)`.
- **Why not just `synchronized` on the order book?** Locking would also be correct, but every thread would compete for the same lock on a hot book. Threads would spend their time blocking and context-switching, and fairness would depend on which thread the scheduler woke up first, not on who arrived first. With confinement, the matching code runs single-threaded and lock-free (simple, cache-friendly, easy to reason about), and the only synchronisation is the hand-off through the queue. This is the idea behind the **LMAX architecture** (LMAX Exchange, written up by Martin Fowler): one business-logic thread per partition, fed by a queue (their *Disruptor* ring buffer), processing millions of orders per second without locks.
- **How it's tested:** a stress test sends 50,000 random limit, market and IOC orders (plus random cancels) from 8 producer threads across all five stocks, then checks that no order was lost or duplicated, that filled + remaining = original for every order, that each order's trades add up to its filled quantity, and that no book is crossed. Other tests prove that two symbols really run in parallel (a latch that would deadlock on a single thread), that each symbol has its own named thread, and that shutdown drains queued work and refuses new work.
- **Likely examiner question:** *"Where exactly is the synchronisation in your exchange, if the order book has no locks?"* — *Answer:* in the `BlockingQueue` hand-off between producers and each worker (plus an `AtomicLong` for ids). Java's memory model guarantees that everything a thread did before `put()`ting a command is visible to the worker after it `take()`s it, so the book is only ever read and written by its own worker. That's thread confinement: the data isn't shared, so it doesn't need locking.

## Step 6 — Spring server (REST + WebSocket)
- **What Spring does here (and doesn't):** Spring Boot runs the web server, turns JSON into Java objects and back, routes URLs to controller methods, and manages the lifecycle (`ExchangeConfig` builds the core objects as beans, starts the exchange, and shuts its threads down cleanly on exit). Spring does **no** exchange logic: controllers convert a request into an `OrderRequest`, hand it to `Exchange`, wait for the worker's answer, and convert it back. Core still has zero Spring imports. The server is an *adapter* (Ports & Adapters).
- **REST vs WebSocket, and why both:** REST (`POST /api/orders`, `DELETE /api/orders/{id}`, `GET /api/symbols`, `/api/books/{s}`, `/api/trades/{s}`, `/api/candles/{s}?interval=1m|5m|15m|1D`) is request/response, which suits actions and loading a page's starting data. A live market needs the server to *push* updates the instant they happen, so `/ws` is a WebSocket using STOMP topics (`/topic/book.RELIANCE`, `/topic/trades.RELIANCE`, `/topic/orders`). Polling REST many times a second would waste requests and still lag behind.
- **Why book updates are throttled:** `MarketDataBridge` is an `EngineListener` (Observer) on the core `EventBus`. On the worker thread it only drops the event into a concurrent map or queue, which is very fast, so matching is never slowed. Every 100 ms a scheduler sends the **latest** book per stock (older unsent snapshots are simply replaced, so at most 10/s per stock) and **all** trades since the last flush as one batch (trades are history, so none are dropped). This keeps the browser smooth even when bots trade hundreds of times a second.
- **Errors and data contracts:** `ApiExceptionHandler` maps exceptions to HTTP codes in one place: unknown stock → 404 (a dedicated `UnknownSymbolException` in core), invalid input or unreadable JSON → 400, exchange shutting down → 503, always with `{"error":"..."}`. Responses use DTO records plus immutable core records (`OrderView`, `Trade`, `BookSnapshot`), never the mutable `Order` entity. Core also gained two Observers for market data: `TradeHistory` (last 500 trades per stock) and `CandleAggregator` (OHLCV candles for every interval, bounded to 500 bars).
- **How it's tested:** controller tests run against the real exchange (no mocks) through MockMvc: resting, crossing, rejected market, 400/404 cases, cancel twice. A full integration test starts the server on a random port, connects a real STOMP WebSocket client, places two crossing orders over REST, and receives the pushed trade and book. A build fix also came out of this: the compiler's `-parameters` flag is needed so Spring can match `@PathVariable`/`@RequestParam` by name.
- **Likely examiner question:** *"Your controller calls an exchange that runs on other threads. How does a web request get its answer?"* — *Answer:* `exchange.submit()` returns a `CompletableFuture` immediately, and the order is queued for the stock's worker thread. The controller waits on the future with a 5-second timeout; when the worker finishes matching it completes the future, and the web thread wakes up with the result. If the worker threw (say, an invalid order), the original exception is rethrown and turned into a 400.

## Step 7 — Trading terminal UI (React)
- **Design system used as-is:** the Claude Design export is copied into `frontend/src/design/`: the token CSS (colours, type, layout, motion, print — the single source of truth for every value) and the reference `.jsx` components with their `.d.ts` prop types, re-exported from `src/design/index.ts`. The terminal (`src/terminal/`) composes those components exactly like the `trading-floor-v2` prototype, but with real data: Masthead → HeadlineBanner → StockTabs → four columns (Markets · chart & tape · order book · ticket & your orders). Day/Night is the `data-edition` attribute; the choice is remembered in `localStorage`.
- **Data flow:** `useMarketData` loads `/api/symbols`, then opens one STOMP connection and subscribes to every stock's `/topic/book.S` and `/topic/trades.S` plus `/topic/orders`. When the selected stock or chart interval changes it fetches REST snapshots (book, last 40 trades, candles). Everything lands in one **zustand** store (`store/market.ts`); components select only the slice they draw, so a trade in TCS doesn't redraw the RELIANCE order book.
- **Two layers of throttling:** the server already batches every 100 ms; the browser then buffers incoming messages in plain arrays and applies them **once per animation frame** (`requestAnimationFrame`), keeping only the newest book per stock. However busy the bots get, React renders at most ~60 times a second.
- **Money stays in paise until the last moment:** the store holds integer paise exactly as the server sends them; `toRupees` divides by 100 only when handing a number to a display component. Typed prices are parsed as text (`parseRupees("2,486.50") → 248650`), never through floats, and the ticket enforces whole quantities, ₹0.05 ticks and a ±10% band around the reference price. Every order goes through a confirm modal; the reply becomes a toast (filled / partial / resting / cancelled / rejected with the engine's reason) and a FILLED rubber stamp. Resting orders appear under "Your orders" with a Cancel button, and fills from other traders hitting them arrive as toasts. A unit test proves a fill is not counted twice (once from the REST reply and again from the stream).
- **Likely examiner question:** *"What happens in the UI when the server goes down?"* — *Answer:* the REST boot fails or the WebSocket closes, so the store's `connection` becomes `offline`. The paper prints the "Market Closed" edition: masthead status *closed*, a "presses have stopped" headline, columns greyed, and the ticket replaced by a disabled "Market closed · exchange offline" button. Meanwhile it retries every 3 s (STOMP auto-reconnects every 2 s) and refetches the snapshots once it's back, with no page reload. Tested with vitest (27 frontend tests: formatting, candle folding, the store, ticket rules, headline, and rendering the page against a fake server, both up and down).

## Step 8 — Trading bots (Strategy)
- **Strategy pattern again:** every bot implements `TradingBot` (`id`, `role`, `everyTicks`, `act(BotContext)`, `withdraw`). `BotRunner` only ever calls `act()`, so the four behaviours are four interchangeable classes: **The Munim** (`MarketMakerBot`) quotes 5 bids and 5 asks around a fair price, one stock per turn; **Momentum Chaser** buys a rising stock and sells a falling one (plus small random "noise" trades); **Panic Seller** dumps a big block 0.5% under the last price when a stock is falling; **The Whale** decides on a 2,000–6,000-share block and works it in 100–300-share slices over many turns (parent/child order). `AbstractBot` holds what they share: id, role and the list of resting orders to cancel later. `StandardBots` is the factory, so a new bot is one new class plus one line (Open/Closed).
- **Bots go through the front door:** a bot sees the market only through `MarketView` (prices, never other traders' orders) and trades only through `OrderGateway` (submit and cancel, like a human). Both are interfaces (Dependency Inversion). In production they are `LiveMarketView`, an Observer of engine events, and `ExchangeGateway`, an Adapter that queues on the worker and waits for the answer. In tests they are `FakeMarket` and `EngineGateway` (real matching, no threads), and a `ZeroRandom` makes every decision predictable. Money stays integer: prices are rounded to ₹0.05 ticks and moved in basis points (1 bp = 0.01%) with `long` maths (`Ticks`).
- **Concurrency:** all bots run on **one** scheduler thread ("bots"), so each bot's own state (its resting orders, the whale's parent order) is thread-confined and lock-free, the same idea as one worker per book. The only cross-thread request is pause/resume from a web thread, a flag in a `ConcurrentHashMap` that the bot thread acts on at its next tick (a paused bot's quotes are withdrawn once). A bot that throws is logged and skipped; the others keep trading. On shutdown Spring stops the bots *before* the exchange, because the runner bean depends on the exchange-shutdown bean.
- **Scorekeeping:** `BotLedger` is another `EngineListener`: every trade moves shares to the buyer and cash to the seller. P&L is marked to market (cash + position × last price). The integration test runs all four bots for 400 ticks on the real five-thread exchange and checks that every stock traded, no book is crossed, prices stayed within 10%, and positions across all traders sum to zero (every share bought was sold by someone). REST: `GET /api/bots`, `POST /api/bots/{id}/pause|resume`. The terminal's "On the Floor" section shows each bot's portrait, status and live P&L; click a bot to pause it.
- **Likely examiner question:** *"Why does your market maker often lose money?"* — *Answer:* adverse selection. It quotes both sides all the time, and the momentum and panic traders only trade with it when they think the price is about to move, so it tends to buy just before falls and sell just before rises. Real market makers defend with wider spreads, faster re-quoting and inventory limits. The Munim pulls its fair price slightly back toward the reference price, which also keeps the simulated market from drifting away for ever.

## Step 9 — Storylines, Correspondents and the newsroom
- **Scenarios are Strategies too:** each storyline (Flash Crash, Bubble, Whale Dump, Calm Market in `Storylines`) implements `Scenario` with three hooks: `begin` (set the scene), `step` (one beat per tick) and `end`. `ScenarioDirector` runs at most one at a time and ends it when its duration is up. A story acts only through `ScenarioStage`: it can sweep the book in a named bot's name ("Panic Seller dumps 1,500 RELIANCE"), and turn bots' dials or pause them. The stage remembers each bot's original settings the first time it changes them and puts them all back at the end (a Memento), so a story can never leave the market permanently bent.
- **Same thread, no new locks:** the director is a `BotRunner.TickHook`, so scripted orders and the bots' own orders come from the one "bots" thread. Web requests (start/stop a story; hire, remove, pause or tune a bot) never touch running state directly: they drop a request in a concurrent queue or flip a value in a concurrent map, and the bot thread acts on it at the next tick. The two dials (`BotTuning`, 0–4) are an immutable record held in a `volatile` field, so the bot thread always sees a whole, current setting. Hired correspondents come from `BotStyle`, an enum whose constants each build their bot class (Contrarian, Noise, a second Maker or Momentum): adding a style is one line, no `switch`.
- **The newsroom (Observer, twice):** `HeadlineWriter` listens to engine events *and* to the director. It files a story when a stock sets a new record move from its reference price (1%, 2%, 3%...), when it gives back two or more levels, when a block of 1,000+ shares trades (naming the bot that hit it, at most once per 20 s per stock), and when a storyline starts or ends. A price wobbling around one line is reported once, not every time it crosses. New headlines are pushed immediately on `/topic/wire` (they're rare, so nothing to throttle), and the banner leads with fresh news for the selected stock, falling back to the price story after 90 s.
- **UI:** the app now has two pages sharing one live connection and one newspaper shell (masthead with page links, banner, toasts, folio): the Trading Floor (now with The Wire) and **Our Correspondents**, with a card per bot (portrait, orders today, P&L, the two dials, send on leave, remove), "Hire a correspondent", and Today's Storylines with run/stop and a NOW RUNNING stamp. Tests: director timing and restore, the four storylines on a real exchange (the flash crash takes RELIANCE down more than 10% inside 60 s, which Step 10's circuit breaker will catch), headline rules, hire/remove/tune and story REST endpoints. In total: 231 core + 27 server + 34 frontend tests.
- **Likely examiner question:** *"A web request changes a bot's settings while the bot thread is reading them. Why is that safe without a lock?"* — *Answer:* the settings are an immutable `BotTuning` record and the field holding it is `volatile`. The web thread replaces the whole record in one write, and `volatile` guarantees the bot thread sees that new reference (and everything in it) on its next read. Since the record can never change after construction, the bot can never see half of an old setting and half of a new one. Anything more complex (adding or removing bots, starting a story) goes through concurrent collections and is applied on the bot thread itself.

## Step 10 — Circuit breaker (State pattern)
- **State pattern:** a stock's trading phase is an object implementing `MarketState` (`OpenState`, `HaltedState`; Step 13 adds the auction). Each state answers the same questions its own way: may an order be accepted (`refusal()`), why are we here (`reason()`), when does this phase end (`until()`), and what comes next as time passes (`onClock`). `TradingSession` is the *context*: it holds the current state inside each `SymbolEngine` and swaps it on a transition. The engine never writes `if (halted)`; it asks the session. `HaltedState` takes the "what follows a halt" decision as a function, so Step 13 can reopen into a call auction without editing the halt class (Open/Closed).
- **The rule (10% in 60 s → 30 s halt):** `CircuitBreaker` compares every trade with the highest and lowest prices of the last 60 seconds. A trade 10%+ below the high (a crash) or above the low (a spike) trips it, so "up 4%, then down 10%" inside a minute is caught. The window's high and low come from `PriceWindow`, two *monotonic deques* (the classic sliding-window-maximum algorithm): a new price evicts every older price it beats, so the front is always the max (or min), and each trade costs O(1) amortised. Prices stay `long` paise; percentages are compared by cross-multiplying, so there's no division and no `double`.
- **What a halt does:** the trade that trips the breaker completes (already matched), then `MarketStatusChanged(HALTED, reason, until)` is published after the usual events. New orders are *rejected* with "trading halted: RELIANCE fell 10.0% in 60 seconds (₹2,458.75 → ₹2,212.50)", but **cancels still work**, so nobody is trapped in the book. A small "exchange-clock" thread drops a `tick` command into every worker's queue every 200 ms, so a halt ends on time even if no order arrives; the tick runs *on the worker*, keeping thread confinement intact. On reopening the breaker starts a fresh window, so the old fall can't trip it again straight away.
- **Everyone hears about it (Observer):** `StatusBoard` keeps each stock's phase for `/api/symbols`; the bridge pushes `/topic/status`; `HeadlineWriter` prints "STOP PRESS: Circuit breaker halts trading in RELIANCE" and later "Trading resumes". The floor turns grey and gets a STOP PRESS stamp, a halt band (alert, countdown to the reopen, what happens next), a halted tab, and a ticket that says "Order entry paused". Tests cover the window maths, trip/no-trip boundaries, the session's transitions, the engine refusing orders but allowing cancels, the exchange clock reopening by itself, the REST API, the headlines, and the Flash Crash storyline actually tripping the breaker.
- **Likely examiner question:** *"Why use the State pattern here instead of a boolean `halted` flag?"* — *Answer:* with a flag, every place that cares (accepting orders, matching, the clock, the UI status) needs its own `if (halted) ... else if (auction) ...`, and each new phase means editing all of them. With State, each phase's behaviour lives in one class, the engine just delegates to the current state, and a transition is swapping one object for another. Adding the call auction in Step 13 is a new class plus a different "reopen" function, with no change to `OpenState`, `HaltedState` or the engine's order path.

## Step 11 — X-Ray
- **What it is:** an explainer that replays how *your* order was matched. When an order from the human trader (`YOU`) arrives, the engine first copies the opposite side of the book (10 levels, every order in each queue with its owner) *before* matching, then hands the copy, the order and the `MatchResult` to an `XRayRecorder`. `XRayDesk` (the recorder) turns that into an immutable `XRay`: the book-before, each fill (price, quantity, whose resting order it met, which level), the outcome, and a list of narration `Step`s. The page replays it step by step: the order slip slides in, levels are circled and numbered ①②③ as they fill, the quantity is struck through, a dashed pencil line marks where matching stopped, and a RESTED stamp appears if part of the order joins the book.
- **Narration is a pure function:** `Narrator` turns the facts into plain English ("The Munim's order at ₹2,486.75 is first in line: 50 shares trade at its price. 150 still to buy.") in a fixed structure: ARRIVE → CHECK → FILL × n → STOP → OUTCOME. It has no state and no clock, so the exact sentences are unit-tested, using the worked example from the design (buy 200 RELIANCE at no more than ₹2,487.50 against asks of 50/80/30 and a level above the limit). It also handles market orders on an empty book, IOC remainders and orders refused during a halt.
- **Cheap when unused:** the engine asks `recorder.wants(request)` first, so capturing full queues only happens for the human's orders; bots' thousands of orders cost nothing. The recorder is a small interface with a `NONE` null object, so the engine has no `if (xrayEnabled)` checks. The desk is written on worker threads and read by web threads, so its bounded store (last 50) is guarded by one lock. On the floor, **X-Ray mode** shows the stamp of the trader holding the most shares at each book level (`LevelSnapshot.mainTrader`, computed per level from its queue).
- **Design decisions:** trades always happen at the *resting* order's price, and the X-Ray makes that visible: a limit buy at ₹2,487.50 pays ₹2,486.75, ₹2,487.00 and ₹2,487.25, not its limit. Time priority is visible too, because each level's queue is shown oldest first. Bot names come from the bot runner through a lazy lookup, because the X-Ray desk must exist before the exchange starts while the bots are created after it. A side fix: the live tape now de-duplicates trades that arrive both in the REST snapshot and on the stream.
- **Likely examiner question:** *"How do you know what the book looked like before the order matched, if matching changes it?"* — *Answer:* on the worker thread, just before calling the matcher, the engine asks the book for `detail(oppositeSide, 10)`, which copies every resting order (id, trader, remaining quantity) into immutable records. Matching then mutates the real book, but the copy can't change. Because all of this happens on the stock's single worker thread, no other order can sneak in between the copy and the match, so the X-Ray is exactly what the order saw.

## Step 12 — Market surveillance (the innovative feature)
- **The idea:** a Surveillance Inspector watches every order and trade *as it happens* and opens an investigation when someone manipulates the market, like a real exchange's surveillance desk (NSE and SEBI run exactly these checks). To have something to catch, a fifth bot joins: **The Spoofer** (`SpooferBot`, a small state machine). It stacks three large bids (5,000–11,000 shares) on neighbouring ticks just under the price, a quarter-second later sells a few shares into the price those fake bids propped up, then pulls the bids before anyone can hit them.
- **Rules are Strategies (Open/Closed again):** each abuse pattern is a `SurveillanceRule` with its own sliding-window state. **Spoofing:** over 30 s, a trader's large orders (≥ 5,000) were more than 85% cancelled, across at least 3 of them. **Layering:** cancels at 3+ prices within 5 ticks on one side, each less than 1 s after placing. **Wash trade:** the same owner on both sides of a trade, or a buy and a sell of the same size at the same price within 0.5 s; two pairs in 30 s. **Pump:** a stock up ≥ 0.5% in 30 s with more than 60% of the aggressive buying from one trader. Each rule has a cooldown, so one burst opens one case, not fifty. The desk runs every *enabled* rule on every event; a new pattern is a new class, and each rule can be switched off from the Rules panel.
- **Cases with evidence:** `SurveillanceDesk` is an `EngineListener`. It keeps an `ActivityLog` (the lives of the last 50,000 orders: placed when, at what price and size, filled or cancelled when) and, when a rule fires, opens a numbered `Case` (SV-0001...) with key figures and the suspect's every order in that stock over the previous 30 s. The Investigations page draws that as a timeline (a line per order from placed to ended, thickness = size, ✕ = cancelled, ● = filled) with the suspicious ones red-pencilled. The Inspector's two rulings: **Dismiss**, or **Suspend**, which adds the trader to `Suspensions` and cancels everything they have resting on every stock (`Exchange.cancelAllFor`, run on each worker). Each engine checks an `OrderGate` before accepting an order, so a suspended trader's orders are rejected ("trader suspended by market surveillance"), and the engine knows nothing about surveillance (Dependency Inversion). Reinstate lifts it.
- **Everyone hears about it (Observer):** new and updated cases are pushed on `/topic/surveillance`, the newsroom prints "Surveillance flags spoofing in RELIANCE; The Spoofer under investigation" and "STOP PRESS: The Spoofer suspended from trading", the floor's book red-circles levels held by a trader under investigation, and the bot list shows them as *flagged*. Live, the Inspector catches The Spoofer within seconds of the market opening. Tests: each rule's positive and negative cases with hand-made events, desk rulings, a live exchange where the Spoofer is caught and then rejected and swept from every book, and the REST API end to end.
- **Likely examiner question:** *"Isn't the market maker also placing and cancelling orders all day? Why isn't it flagged?"* — *Answer:* the rules are about the combination that only manipulation produces. The Munim's quotes are small (50–300 shares, under the 5,000 "large" threshold), spread about 4 basis points apart (more than 5 ticks), and live over a second before being replaced, and it trades on both sides. The Spoofer's orders are huge, stacked within 5 ticks, pulled within a quarter of a second, and only ever on the side it isn't really trading. That's why each rule has several conditions: any one alone would flag honest traders.

## Step 13 — Call auction
- **What it is:** the way a halted stock reopens, as on real exchanges (NSE runs one every morning in its pre-open session, and after a circuit-breaker halt). After the 30-second halt the stock enters `AuctionState` for 30 seconds: limit orders are *collected* but not matched (the book may be crossed on purpose; `OrderBook.addForAuction` skips the "would cross" check), market and IOC orders are refused, and an `AuctionUpdate` with the **indicative price** is published after every change. When the auction closes, everything that crosses trades at **one single price**, then continuous trading resumes. It plugged in as one more State (`HALTED → AUCTION → OPEN`): the halt's "what comes next" function now builds an `AuctionState`, and no existing state class changed.
- **The algorithm (`CallAuction`):** for each price p in the book, demand D(p) = shares bid at p or higher and supply S(p) = shares offered at p or lower, so min(D, S) can trade. Pick the price that trades the most shares; break ties by the smallest leftover imbalance |D − S|, then by the price closest to the last trade. Only prices that appear in the book need checking, because volume only changes at those prices. Then *uncross*: match crossing orders best price first (and oldest first within a price), exactly like continuous matching, except that every trade is printed at the auction price. Worked example (tested): bids 105×100, 104×200, 102×300 vs asks 100×150, 103×250, 104×100 → ₹103 trades 300 shares (₹104 also trades 300 but with a bigger imbalance).
- **Why nothing is left crossed:** if after uncrossing at the max-volume price p a bid b were still above an ask a, then at price a more shares would trade (all the filled shares plus those two orders), contradicting p being the maximum. The tests check the book is uncrossed after every auction.
- **Around it:** bots join the auction like real traders: an IOC refused with "only limit orders" is re-sent as a limit order, so the auction gets real buy and sell interest. The newsroom prints "RELIANCE call auction under way" and "Trading resumes in RELIANCE at ₹2,204.85 (the call auction crossed 860 shares at one price)"; the floor shows an auction band (indicative price and volume, buy/sell interest bar, countdown to the bell), a faint CALL AUCTION stamp, a crossed book, and a "Limit only" ticket. Two refinements came out of watching it live: the ticket's ±10% band now follows the last traded price (after a 10% crash the old band refused every realistic price), and layering now requires the stacked orders to be in the book *at the same time*, so a market maker re-quoting one level at a time is no longer flagged.
- **Likely examiner question:** *"Why reopen with an auction instead of just resuming continuous matching?"* — *Answer:* after a halt, orders pile up on both sides with very different ideas of the price. Resuming continuous trading would let whoever arrives first sweep a thin book at extreme prices (the very thing the breaker stopped). An auction gathers everyone's orders first and finds the one price where the most shares change hands, so price discovery happens on the full picture, fairly for everyone in the auction, and the market reopens at a price both sides accept.

## Step 14 — Benchmark and hardening
- **Benchmark (`Benchmark`, `./bench.sh`, `docs/BENCHMARK.md`):** two measurements on a reproducible random flow with a JIT warm-up. The **engine alone** (one thread, no queue) did 169k orders/s with a median of 4.6 µs per order. The **whole exchange** (4 producers, each waiting for its answer, through the five worker queues) did 72k orders/s with a 43 µs median round trip, on a 2-CPU container. The hand-off between threads costs about ten times the match itself: that's the price of thread confinement, paid for simple lock-free matching code.
- **The benchmark found a real bug:** the first run did 3,485 orders/s. X-Ray's "main trader per level" walked every order in each level's queue on every book update (O(queue length) × 10 levels per order). Keeping a running per-trader total inside `PriceLevel`, updated on add, fill and remove, made it **48× faster** with identical behaviour. A new test checks the total stays right through fills and removals.
- **Hardening:** (1) **Fat-finger limits** in `OrderRequest` (at most 10 lakh shares, ₹10,00,000 a share, a 32-character trader id), so an order can't overflow the `long` arithmetic or flood the book; the API answers 400 with the reason. (2) **Bounded back-pressure:** a full worker queue (100,000 commands) makes a producer wait at most one second, then the order is refused ("RELIANCE is too busy; try again" → HTTP 503) instead of blocking a web or bot thread for ever. (3) **Every in-memory collection is bounded:** recent orders (50,000 per stock), order routes (500,000), trades (500 per stock), candles (500 per interval), the surveillance activity log (50,000), cases (200), the Wire (50), X-Rays (50). The server can run all day without growing. (4) A React **error boundary** ("The presses jammed") replaces a blank page if any component crashes. (5) Listener isolation (from Step 4) means one failing observer can't stop matching.
- **Soak test:** all five bots, three storylines back to back (crash → halt → auction, bubble, whale dump), surveillance with a real suspension of The Spoofer, and the newsroom, for 300 simulated seconds on the real multi-threaded exchange. Then it checks the invariants: every event well-formed, positions across all traders sum to zero, more than 1,000 trades happened, and no book is crossed outside an auction. Totals now: 277 core, 32 server and 44 frontend tests.
- **Likely examiner question:** *"How would you make it faster?"* — *Answer:* measure first (that's how the X-Ray bug was found). Then: (a) replace the `LinkedBlockingQueue` hand-off with a pre-allocated ring buffer (LMAX Disruptor) to cut the 40 µs of queueing; (b) avoid allocating a new `BookChanged` snapshot after every order by coalescing book events per batch, as the WebSocket bridge already does every 100 ms; (c) use primitive collections (e.g. a `long`-keyed map for order ids) to avoid boxing; (d) pin each worker to its own CPU core. The matching algorithm itself (price-time priority over `TreeMap` levels and `ArrayDeque` queues) is already O(log levels) per order.

## Step 16 — Front page, routing and the demo autopilot

- **Demo autopilot (`#/demo`, `./demo.sh`):** the tour is **data**: an array of 13 `DemoStep`s, each with a page, a caption, an optional action (place an order, start the Flash Crash, open the Spoofer's case, suspend it) and how long to stay. Steps that depend on the market wait for a condition (the breaker tripping, the auction starting, the reopening) with a maximum, so the tour never stalls. A small runner hook (`useAutopilot`) moves between steps on a quarter-second clock, and the caption bar offers Pause, Skip and Stop. The full tour was run end to end in a browser: about 3 minutes and no errors. Under it, `stepDone` is a pure function with unit tests. `demo.sh` starts everything, waits for both servers, and opens the browser on the tour.
- **Polish from watching it run:** toasts move clear of the front page's navigation; only critical surveillance cases raise a toast (all cases still go to The Wire and the Surveillance column); and the Investigations page can be pointed at a specific case, so the tour's "ruling" shows the case being decided. Totals: 277 core, 32 server and 49 frontend tests.
- **Likely examiner question:** *"Why is the demo a list of data instead of code?"* — *Answer:* the steps are what changes most often (wording, order, timing), and as data they're easy to read, reorder or extend. The logic that runs them (show the page, run the action once, wait for time or a market condition, move on) is written once and tested once. It's the same idea as the Strategy and Open/Closed parts of the engine: separate the part that varies from the part that stays the same.
